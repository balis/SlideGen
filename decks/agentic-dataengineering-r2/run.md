Lecture Request
Topic: Data Engineering in the Age of Artificial Intelligence — Data Preparation for ML, AI Agents in Pipeline Automation, and Vector Databases
Course: Data Engineering, graduate level (Lecture 7)
Prerequisites: relational databases and SQL, Python, batch ETL, basic distributed data processing (Spark DataFrames), data quality/contracts (Great Expectations or equivalent), basic ML concepts (training vs. inference, features, embeddings as a notion)
Duration: 90 minutes (~50-70 slides)
Learning objectives:

1. Explain why ML consumption changes the contract on a data pipeline relative to BI: silent distributional failure versus visibly-wrong dashboards, the "data science hierarchy of needs" placing 70–80% of effort in the data layers, and the shift from data-as-query-target to data-as-versioned-time-aware-artifact. Frame feature engineering as a stateful pipeline stage in which fit-time statistics (means, vocabularies, quantile boundaries) are persisted and reapplied identically at inference.
2. Analyze training/serving skew as the central ML-data failure mode: distinguish its two sources (divergent batch-training vs. online-inference code paths; point-in-time correctness violations), and demonstrate a temporal leak on a realistic schema (transactions + customer dimension + timestamped labels) in which a naive join leaks future information. Contrast skew (a consistency mismatch between two code paths) with concept/distribution drift (the world changing under a deployed model) so the two are not conflated.
3. Describe point-in-time / as-of joins as the mechanism that prevents temporal leakage and the feature store as the architecture that prevents skew and feature duplication: the offline-store / online-store / shared-transformation-definition pattern, the second consistency problem it introduces, the ANSI window/lateral implementation versus dialect-specific ASOF JOIN (DuckDB, ClickHouse, kdb+), and when NOT to adopt a feature store (single model, single team, batch-only inference).
4. Design a reproducibility strategy for ML datasets by recognizing that point-in-time correctness, dataset versioning, and embedding-model versioning are one temporal problem at three layers — "what was the data state when this artifact was produced, and can it be reconstructed." Compare lakehouse time-travel (Delta/Iceberg snapshots), content-addressable data versioning (DVC), and git-for-data over object storage (lakeFS), with their cost and operational tradeoffs.
5. Compare data quality and observability for ML against pipeline-liveness monitoring: schema drift vs. distribution drift vs. concept drift defined and distinguished; distributional validation via PSI and KL divergence on feature distributions; and why data contracts catch structural breaks but not silent distributional shift. Include the failure mode of offline metrics improving while online metrics regress.
6. Describe embedding generation as a first-class, version-sensitive pipeline stage: model selection (dimension vs. quality vs. cost), batch throughput and rate-limit handling against hosted embedding APIs, idempotent re-embedding, and the hard dependency in which the embedding model is baked into every stored vector so that changing it invalidates the entire index and forces a full re-index.
7. Evaluate vector databases as a storage-and-search primitive: why exact k-NN is O(n·d) per query and infeasible at scale; the index families HNSW (graph), IVF (partition), PQ (compression), and DiskANN (disk-resident) with their build-time / query-time / recall / memory tradeoffs; recall-vs-latency as a tuned property exposed through parameters (efSearch, nprobe, m, nbits) rather than a fixed one; metadata pre- vs. post-filtering and its interaction with ANN; upsert/delete and consistency semantics; and recall as a silently-violated SLO rather than a raised error. Include the dedicated-vector-DB (Pinecone, Weaviate, Qdrant, Milvus) vs. pgvector-on-existing-Postgres decision.
8. Analyze RAG retrieval as a two-stage data pipeline rather than a single similarity lookup: chunking strategy as a schema-design decision; hybrid retrieval combining sparse BM25 and dense ANN fused via Reciprocal Rank Fusion; cross-encoder re-ranking as a second stage; and the clean separation in which hybrid search improves recall (lexical matches the dense model ranks too low) while re-ranking improves precision (reordering only the already-retrieved set, so it cannot fix recall). Include the canonical failure of a relevant chunk retrieved but ranked just outside top-k.
9. Evaluate AI agents for pipeline automation by first defining an agent precisely (an LLM in a loop with tool access and a stopping condition, distinct from a single LLM call and from rule-based automation), then assessing where one earns its place versus acting as an expensive nondeterministic cron job. Cover use cases with failure modes (schema mapping/entity resolution, text-to-SQL with a verification layer, data-quality triage, lineage/doc generation); the architectural principle of narrowing the nondeterministic boundary, wrapping agent output in deterministic validation, and treating agents as DAG nodes rather than orchestrators; and the suggest-only → human-approval-gated → bounded-autonomous maturity ladder, motivated by a documented production-incident case study.
10. Recognize the governance, privacy, and evaluation constraints specific to AI-oriented pipelines: that embeddings and trained models are derived data which can leak source content, so deletion/GDPR obligations must propagate to vectors and training sets; lineage extended to ML artifacts (which data version and which embedding model produced which model/index); least-privilege tool scoping and auditability for agent actions; prompt-injection and data-poisoning as pipeline security surfaces; and the joint evaluation of AI-assisted workflows on reliability, cost-per-invocation, and latency budgets.
